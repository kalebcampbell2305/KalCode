# Campaign Z12 — KalVoice

Branch `z12/kalvoice`. Goal: KalVoice as the product's voice layer: one push-to-talk key that
runs KalCode commands, dictates into any input, or asks the user's own provider, with on-device
speech, honest metering and latency as the flagship quality. Behaviour: `docs/KALVOICE.md`.

Results are marked PASS only when executed on this branch (Windows 11, Node 24, Rust 1.97).
PENDING-INTEGRATION means the Z12 side is built and tested and waits for another campaign or the
lead. FLAGGED means it works but misses a target or needs a decision.

## Measurements

Reference machine: this Windows 11 PC (24 logical CPUs), whisper.cpp CPU build (no GPU; the
Vulkan SDK isn't installed), release profile, `tiny.en` (78 MB). Other agents were building on
the same machine during some runs, so single runs vary; the numbers below are from
2026-09-24.

**Benchmark** (`latency_bench`, 18 fixtures × runs, real-time playback through the same
voice controller, streamer and router the app uses; injected audio source, so stage 1 measures
the controller, not the device):

| Stage | Idle, 3 runs (n = 54) p50 / p95 / p99 | CPU load (4 busy threads) + 20 workspaces, 2 runs (n = 36) p50 / p95 / p99 | Target p95 |
| --- | --- | --- | --- |
| key down → mic (controller) | 0.0 / 0.1 / 0.1 ms | 0.0 / 0.1 / 0.1 ms | 50 ms |
| speech → first partial | 293 / 361 / 365 ms | 311 / 403 / 575 ms | — |
| key up → final transcript | **87 / 317 / 474 ms** | **85 / 371 / 784 ms** | 250 ms |
| final → recognized (grammar + routing) | 0.0 / 0.3 / 0.7 ms | 0.0 / 0.4 / 0.5 ms | 5 ms |
| recognized → executed (fixture executor) | 0.4 / 0.9 / 23 ms | 0.4 / 0.9 / 0.9 ms | 100 ms |

- 52 of 54 idle takes reused the last partial (no decoding after key up); the two over budget
  are the final passes that ran because the fixture's tail wasn't silent.
- Routing on the fixtures: 36 of 36 command takes routed as commands (open dashboard, open
  "authentication" workspace, open four Codex threads in three speeds, "show what's waiting for
  me"); dictation and the unsupported "split Claude and Codex side by side" went to Request, as
  they should with today's contract.
- **Real microphone** (`mic_probe 15`, default Windows input): first open 60.8 ms, p50 10.8 ms,
  p95 60.8 ms, max 195.3 ms. The p95 is the cold first open; warm opens are ~11 ms.
- **Recognized → visible action in the app** is recorded by the UI after the browser paints
  (`kalvoice_latency_record`) and shown in the developer view; it isn't part of the benchmark.
- History: `base.en` was the first default (key up → final p50 325 / p95 1,257 ms idle); a full
  30 s context pass took about 4 s. Sizing the audio context and token cap to the audio, keeping
  the decoder state, streaming partials and reusing the last partial brought `tiny.en` to the
  numbers above. Quantized models (base q5_1/q8_0, tiny q5_1) were slower on this CPU.

**Streaming ASR research.** whisper.cpp re-decodes the growing buffer (not a true streaming
model), so the key-up tail costs one short pass whenever the speaker is still talking at
release. Options, in order: (1) sherpa-onnx (Apache-2.0) with a streaming zipformer
transducer, which emits text as audio arrives instead of re-decoding (not evaluated on this
machine yet), behind the same `SpeechRecognizer` trait, as a consented, SHA-pinned download; (2) whisper.cpp
with Vulkan/CUDA where a GPU exists; (3) the opt-in pre-opened microphone for the cold first
open. None is in this branch.

**Budgets file.** `crates/kalvoice/benches/budgets.json` holds the product targets and a
regression baseline (key up → final p95 1,500 ms, the rest equal to the targets). `--check`
fails on the baseline and prints "over target" between the two.

## Contract change requests (lead-owned)

1. `ActionOrigin::KalVoice { request_id }` on `NormalizedAction` and a Z4 entry point that
   accepts non-thread origins (today `validate_action` requires a thread id and
   `insert_approval` always writes `origin_kind = 'thread'`), plus an `ActionKind` for runtime
   operations (create/resume threads). Then `ConfirmGate` is replaced by Z4 approvals.
2. `KalVoiceIntent` additions from the owner's list: `Split`, `Resize`, `Focus`, `Search`,
   `Close`, `SwitchProvider`, `RequestPermissionModeChange` (request only, never Bypass),
   `OpenDashboard` (today `Navigate`) — CONTRACTS_ADVANCED §8.
3. An event for the talk route (`kalvoice.talk_routed { request_id, route }`); today the route
   is visible only through which existing events follow.
4. `KalVoiceMode` still has `dictation | command`; push to talk uses `command` for every take.
   A single `talk` mode would say what happens.

## Missing toolchain and follow-ups

- libclang/LLVM isn't installed on the reference machine; builds with the speech engine used a
  libclang from the PyPI `libclang` wheel via `LIBCLANG_PATH`. CI needs LLVM for
  `kalvoice-whisper`.
- Linux: microphone capture and the OS voice need ALSA and speech-dispatcher dev packages in CI.
- `docs/DEVELOPMENT.md` port table has no row for z12 (1438 UI, 9438 E2E).
- Pending confirmations live in memory: they disappear on restart (nothing runs).
- Opt-in pre-opened microphone (for the cold first open) isn't built.
