# Production account schema recovery

Production's migration ledger reported 0005 and 0006 applied, but schema metadata showed the older account/billing shape. The pending 0007 social-identity migration applied successfully; 0008 then failed because `billing_checkout_intents` did not exist. The API code deployment was held. No account, session, payment, or entitlement rows were exported for diagnosis.

The retained schema-only fixture reproduces that exact shape. The guarded one-time SQL in `tooling/admin/sql/20260926-account-schema-recovery.sql` brings it to the current canonical 0005 contract without rewriting numbered migration history. It checks the exact five affected legacy table definitions and absence of the new objects before changing anything. Execute the entire file in one D1 batch; do not split statements. A mismatch or repeat execution must fail atomically. Fresh databases already created from current migrations do not need this recovery.

Existing account IDs, emails, provider identities, session hashes/revocations, subscriptions, billing customer bindings, grants, and audit records are preserved. Existing accounts retain their prior usable access through `activated_at = created_at`. Legacy sessions remain desktop sessions. Legacy webhook receipts lack an authenticated subscription-subject binding. The repair therefore requires this table to be empty in the same transaction; any processed or pending receipt blocks recovery without changing data. A production aggregate probe reported zero receipts. Never guess a subject or treat an unfinished receipt as processed. No Stripe request, charge, account linkage, or new entitlement is created by the repair.

Run the registered `d1-legacy-account-recovery.test.ts` first. It proves the original migration failure, synthetic data preservation, nonempty legacy webhook denial, exact schema parity with a fresh canonical database after 0008/0009, foreign-key consistency, D1 quick-check, replay denial, and unknown-partial-schema rollback. Then run the complete API suite and typecheck. Independent review is required before production application.

Production sequence: deploy the tested API commit with `--keep-vars --var ACCOUNT_SCHEMA_MAINTENANCE:true`; prove representative auth, account and webhook routes return 503 before dependency construction; allow old requests to drain; record D1 Time Travel bookmark; confirm schema metadata still matches the reviewed legacy fixture; apply the guarded recovery file; apply remaining numbered migrations 0008/0009; compare schema metadata with the tested canonical shape; deploy the same tested API commit with `--keep-vars --var ACCOUNT_SCHEMA_MAINTENANCE:false` and encrypted bindings preserved; perform bounded live auth probes. Verify all four encrypted OIDC binding names after both deployments. Keep checkout disabled. Do not restore a historical Worker version containing plain-text OAuth credentials.

Rollback is forward-preserving by default: leave the additive account fields and new tables intact and revert only compatible application code. A D1 Time Travel restore requires stopping writes and adjudicating intervening account/identity/billing changes; never restore the bookmark blindly or discard newly created social identities. Failure of any SQL guard requires inspection, not removal of the guard.
