# Campaign Z4 — Permission Engine

Branch `z4/permissions`. Goal: a deterministic, fail-closed permission engine that every provider,
agent, KalVoice action and automation passes through, with persistence, an immutable audit trail,
the approval UI and Settings. Semantics: `docs/PERMISSIONS.md`.

Results are marked PASS only when executed on this branch (Windows 11, Node 24, Rust 1.97).
PENDING-INTEGRATION means the Z4 side is built and tested against fakes and waits for another
campaign's code to be wired.

## Engine design

`paths` / `command` / `network` → `classify` (scopes, opaque, sensitive, fingerprint, subjects) →
`policy::evaluate` (pure) → `service` (persistence, events, audit). The baseline function is the
single source for both enforcement and the Settings profile tables. `open_request` never trusts
its input decision. `evaluate` combines the caller's mode with the stored thread mode (stricter
wins).

## Integration seams and exact wiring

**Z1 (workspaces).** Implement `kalcode_permissions::WorkspaceRoots` (`fn root(&self, workspace_id)
-> Option<PathBuf>` returning the workspace's canonical root). In `apps/desktop/src-tauri/src/lib.rs`
replace `PermissionState::unwired(state.core.clone())` with
`PermissionState::new(state.core.clone(), Arc::new(<Z1 roots>), Arc::new(<Z3 store>))`.

**Z3 (threads).** Implement `ThreadModeStore` over the `threads` table: `thread(id)` →
`ThreadSummary`, `set_mode(id, mode, profile_id)` (persist `permission_profile_id` for Custom),
`custom_profile_id(id)`. Hold `PermissionState::service()` as your `Arc<dyn PermissionGate>` and:
1. for each adapter `ApprovalRequired`/tool call build a `NormalizedAction` (thread/workspace ids
   must be UUIDs) → `gate.evaluate(&action, thread.mode)`;
2. `Allow` → run; `Deny` → send the denial with `decision.reason`; `Ask` →
   `gate.open_request(action, mode, decision)` and set the thread to `waiting_for_permission`;
3. subscribe to the event bus and forward `approval.approved` / `approval.denied` /
   `approval.expired` for that `request_id` to the provider session;
4. call `gate.expire_for_thread(thread_id)` when a thread stops, is interrupted, or its process exits;
5. `pending_approvals` on `ThreadSummary` = count of `approval_list { status: "pending" }` for the thread;
6. new threads start in `permission_settings_get().defaultMode` (and `defaultProfileId` for Custom).

The executor must re-check at execution time (open files without following unexpected links) —
the engine decides at evaluation time.

**Z5 (Dashboard).** Inside the shell (already wrapped in `PermissionsProvider`):
`const { pending, decide } = usePermissions();` and render
`<ApprovalPrompt request={request} onDecide={decide} headingLevel={3} />` per request (exported from
`apps/desktop/src/surfaces/permissions/index.ts`). The primitive `PermissionPrompt` is in
`@kalcode/ui/components`. IPC arguments are top-level camelCase: `approval_list { status: "pending" }`,
`approval_decide { requestId, decision }` — matching Z5's client.

**KalVoice (Z12).** Route consequential intents through the same gate as `Actor::KalVoice`
actions; KalVoice can't call `decide`, `set_thread_mode` or `update_settings` successfully
(`forbidden`, audited).

## Migration ordering

`0005_permissions.sql` lives in `crates/native-core/migrations/` and is exposed as
`kalcode_core::db::PERMISSIONS_MIGRATION` but is **not** in `MIGRATIONS` on this branch, because the
runner requires a gap-free sequence and 0002–0004 belong to Z1–Z3. It has no foreign keys into their
tables, so it applies after any of them. On this branch, `kalcode_permissions::branch` supplies
no-op placeholders for 0002–0004 (tests and isolated dev runs only; never the owner's data).

At integration (after Z1–Z3 are on `main`):
1. append `PERMISSIONS_MIGRATION` to `kalcode_core::db::MIGRATIONS` after 0004;
2. delete `crates/permissions/src/branch.rs` (+ `pub mod branch;`) and `branch_migrations()` in
   `permission_commands.rs`; change `Core::open_with_migrations(config, &…branch_migrations())`
   back to `Core::open(config)` in `lib.rs`; point the tests' `open_core` at `Core::open`;
3. the tripwire test `placeholders_must_not_outlive_the_real_migrations` fails as soon as
   `MIGRATIONS` has more than 0001, so step 2 can't be forgotten.
Development data folders created on this branch record placeholder checksums for 0002–0004 and
must be discarded after integration.

## Contract change requests (for the lead)

1. **`ApprovalRequest`**: add `allowedDecisions: ApprovalDecision[]`, `grantCoverage: string`,
   `context: { threadName, workspaceName, providerName }`, `createdAt`, `expireReason`. Z4 returns
   these today as `ApprovalView` (a superset via `#[serde(flatten)]`), so adopting them is additive.
2. **IPC**: add `permission_settings_get` / `permission_settings_update` to `docs/CONTRACTS.md`, and
   `profileId?` to `thread_set_permission_mode` (Custom mode needs a profile).
3. **`ThreadSummary`**: add `permissionProfileId: string | null` (Custom threads).
4. **`PermissionScope`**: consider an explicit `tool.unknown` scope; unrecognized tools currently
   report `terminal.execute` (opaque).
5. **Event**: `permission.mode_changed` covers the default-mode change with `threadId: null`;
   a dedicated `permission.default_mode_changed` event would make the activity feed clearer.
6. **Provider adapters (Z2)**: normalized ids — `NormalizedAction.threadId`/`workspaceId` must be
   UUIDs (the gate denies anything else).

## Known issues

- **WebView trust.** Approvals and Bypass arrive over IPC from the WebView, which the security
  model treats as possibly compromised. The native side enforces confirmation flags and audits
  every change, but a compromised WebView could still answer requests. Recommended follow-up: a
  native (out-of-WebView) confirmation for Bypass and for remote-consequential approvals.
- **Time of check / time of use.** Containment is decided at evaluation; executors (Z2/Z3) must
  open files without following links that appear later.
- **Hard links** to files outside the workspace are not detected (creating one is caught, since
  its target path is outside).
- **Script internals** (`npm test`, `make`, `./build.sh`) are classified as execution; KalCode
  doesn't read them. Git hooks and repository config can run code on read-only git commands in a
  hostile repository.
- **Case-insensitive program names**: `GIT STATUS` is treated as `git status` (a PATH-resolved
  binary with a differently cased name would need to exist on PATH already).
- **Allow via rule** is supported by the engine and IPC but deliberately not offered in the prompt;
  there is no UI yet to list or revoke grants and rules, or to edit Custom profiles.
- The approvals scenario, thread names and provider names in UI tests come from the in-memory
  transport; real data arrives with Z3.
- CI has not run this branch (no remote).
